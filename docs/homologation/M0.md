# Homologação M0 — fundação técnica (S01/S02)

Executada com dados sintéticos, no ambiente local (`compose.yml`, Docker Desktop,
Docker Engine 29.7.2), sem qualquer VPS ou dado real envolvido. Cada roteiro
abaixo foi de fato executado (via `python manage.py shell` com um script de
verificação e via `django.test.Client` contra a pilha real de middlewares e
views) — não é apenas leitura de código. Nenhuma suíte automatizada foi criada
(DEC-20); os scripts usados aqui são roteiros manuais de homologação, descartados
após a execução, não testes unitários do produto.

## Pré-condição

- Dois tenants fictícios: "Clinica A Ltda" (`clinica-a`) e "Clinica B Ltda" (`clinica-b`).
- Um usuário (`doctor@example.com`) com Membership `doctor` em A e `owner`+`doctor` em B.
- Um usuário técnico (`tech-admin@example.com`) com `is_staff=is_superuser=True`.
- Todos os sete serviços locais convergiram para `healthy` antes do roteiro
  (`docker compose ps`), com `EMAIL_ENABLED=SMS_ENABLED=AI_ENABLED=False`.

## H-02 — Autenticação, sessão e vínculos

- [x] Login por e-mail normalizado funciona; `User.objects.create_user(email='Doctor@Example.com', ...)`
  gravou `doctor@example.com` (minúsculas). Tentar criar um segundo usuário com
  `DOCTOR@example.com` foi rejeitado pelo banco (`UniqueConstraint(Lower('email'))`).
- [x] MFA (TOTP) e recovery code funcionam: dispositivo confirmado com token
  válido; login por `POST /accounts/login/` com senha correta entra em estado
  "MFA pendente" (sessão sem `_auth_user_id`); `POST /accounts/mfa/challenge/`
  com o token TOTP autentica a sessão (`django_otp.login` marca `is_verified()`).
  Um recovery code de 3 gerados foi consumido com sucesso uma vez; a segunda
  tentativa com o mesmo código foi rejeitada (`consume_recovery_code` retorna
  `False` na reutilização).
- [x] Usuário participa de duas clínicas com papéis distintos
  (`{'doctor'}` em A, `{'owner','doctor'}` em B) e o `AccessContext` resolvido
  reflete o papel correto por tenant selecionado na sessão.
- [x] Vínculo revogado deixa de autorizar: após `Membership.status = REVOKED`
  na clínica A, `build_access_context` retornou `None` para essa clínica na
  requisição seguinte (sem qualquer invalidação de sessão necessária — o
  contexto é reconstruído a cada requisição), enquanto o acesso à clínica B
  permaneceu válido.
- [x] Senha/token não aparecem em log: `base.logging.RedactSensitiveDataFilter`
  testado diretamente — `password='S3cr3t!' token=abcdef123456` vira
  `password=[REDACTED]' token=[REDACTED]`.
- [x] Limite de autenticação: 7 tentativas de login com senha incorreta para a
  mesma conta ativaram `accounts.throttling.is_throttled` (limite de 5 em
  15 min, com atraso progressivo por tentativa).

## H-03 — Isolamento em todas as superfícies (básico)

- [x] Ausência de vínculo ativo nega resolução: sem tenant selecionado, com
  e-mail não confirmado, ou com Membership revogada, `build_access_context`
  retorna `None` — o middleware `tenancy.middleware.TenantMiddleware` responde
  404 para qualquer rota `/app/...` nesses casos.
- [x] Manipular o tenant não concede acesso: sessão com `tenant_id` da clínica A
  mas `Host` correspondente a um domínio (`TenantDomain`) registrado para a
  clínica B nega o acesso (`_hostname_matches_tenant` retorna `False`).
- [x] FK cruzada rejeitada pelo banco: `Membership` tem
  `UniqueConstraint(tenant, id)` (nome `tenancy_membership_tenant_id_uniq`,
  confirmado via `pg_constraint`) e o helper genérico
  `base.db.composite_tenant_foreign_key` está pronto para as próximas sprints
  aplicarem a FK composta `(tenant_id, referenced_id)` sempre que um novo
  model tenant-scoped referenciar outro (ainda não há esse relacionamento
  concreto em S02 — `Membership` só referencia `Tenant`/`User`, que são
  globais). Essa demonstração completa entre dois models tenant-scoped fica
  para S03-T04 (`Patient`) e S04-T04 (`Appointment`), que dependem
  explicitamente de S02-T05 no PRD.
- [x] Admin/painel técnico/documentação não ficam disponíveis a usuários
  comuns: ver H-19 abaixo — os mesmos três testes cobrem esta linha.

## H-19 — Admin e documentação

- [x] `/admin/login/` responde 200 sem autenticação (para permitir o próprio
  login). Autenticado como superusuário técnico **sem MFA confirmada**:
  `/admin/` responde 302 (negado, sem revelar conteúdo);
  `/admin/dj-celery-panel/` responde 404; `/technical-docs/` responde 404.
  Após confirmar MFA e reautenticar (`django_otp.login`), `/admin/` responde
  200.
- [x] As três rotas de painel (`dj_control_room_base`, `dj_celery_panel`,
  `dj_control_room`) estão registradas sob `/admin/...` e protegidas por
  `base.middleware.TechnicalPanelMFAMiddleware` (exige `is_superuser` +
  `is_verified()`) além do próprio `REQUIRE_SUPERUSER=True` de cada pacote
  (`DJ_CONTROL_ROOM_BASE_SETTINGS`, `DJ_CONTROL_ROOM_SETTINGS`,
  `DJ_CELERY_PANEL_SETTINGS`). `admin.site` é substituído globalmente por
  `base.admin.TechnicalAdminSite` via `AdminConfig.default_site`, então os
  registros automáticos desses três pacotes (`@admin.register` no `admin.py`
  de cada um) herdam a mesma política sem exigir alteração no código deles.
- [x] `/technical-docs/` usa a view já existente (`ops/docs.py`, de S01),
  agora efetivamente registrada em `core/urls.py`; nega com 404 para qualquer
  usuário sem `is_staff`+`is_superuser`+MFA verificada, e nunca fica em cache
  público (`Cache-Control: private, no-store`).
- **Pendente para sprints futuras:** mascaramento de argumentos/resultados
  sensíveis em tarefas Celery — não há, nesta sprint, nenhuma tarefa real com
  payload sensível (`base.tasks.operational_ping` é trivial); revisar quando
  `communications`/`ai`/`documents` registrarem tarefas reais (S07+).

## H-21 — Deploy técnico (revisão após mudanças de S02)

- [x] Os sete serviços locais convergiram novamente para `healthy` após a
  reconstrução da imagem com o código de S02 (`docker compose build app && \
  docker compose up -d`); `python manage.py check` sem problemas.
- [x] **Achado real corrigido nesta sprint:** o volume local do PostgreSQL
  ainda continha o schema antigo de `accounts_user` (chave `bigint`) criado
  durante a verificação de S01, e a tabela `django_migrations` registrava
  `accounts.0001_initial` como já aplicada — mas o arquivo de migration foi
  substituído (novo modelo de usuário, chave `UUID`) sem trocar de nome. Isso
  gerou um erro real de tipo incompatível (`uuid` x `bigint`) ao tentar criar a
  FK de `Membership.invited_by`. Corrigido derrubando o volume
  (`docker compose down -v`) e reaplicando as migrations do zero — seguro
  porque não existe dado real nesta fase (DEC-20/pré-piloto). Lição registrada
  para não reaproveitar nomes de migration ao mudar radicalmente um model
  antes do primeiro deploy real.
- [x] Nenhum secret aparece em log/status; `docker compose ps` e os logs dos
  serviços não expõem senha/token (mesma verificação de S01, reconfirmada).

## Limites explícitos desta homologação

- Não cobre H-01 (onboarding/convites — S03), H-04 a H-18 e H-20/H-22/H-23,
  que dependem de funcionalidades ainda não implementadas.
- A verificação usou `django.test.Client` contra a pilha real de middlewares e
  views dentro do contêiner `app` já em execução — não é uma suíte de testes
  do produto (DEC-20), é evidência manual descartável desta sprint.
- Nenhuma clínica real, certificado, ou dado de paciente foi usado.
